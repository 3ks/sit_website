01

Worktree first

Worktrees sit at the top of the sidebar, not three menus deep. Create one, switch with a double-click, and see every worktree's HEAD marked on the graph. No more stash, switch, unstash.

02

Remote native

Open a repository where it lives. SIT connects over SSH, places a small agent in ~/.sit without root, and runs git on that machine. Nothing to clone, nothing to keep in sync.

03

Byte-level fidelity

Paths are bytes, not strings. SIT reads git only through its stable machine formats, so non-UTF-8 names, spaces and renames arrive exactly as git stores them.

Everyday Git

The whole of Git, at the level you want to work.

Commit a file, a hunk or three lines. Read a history of two hundred thousand commits without waiting for it to load.

  • A graph that stays fast. History streams in pages and only the visible rows are drawn, so giant repositories scroll like small ones.
  • Stage precisely. By file, by hunk or by selected lines, in inline or side-by-side diffs with syntax highlighting.
  • Resolve conflicts in place. A three-way merge editor with an editable result, for merge, rebase, cherry-pick and revert.
  • Ask where a line came from. File history that follows renames, blame, and the history of just the lines you selected.
  • Stay in the window. A file tree, a built-in editor, bookmarks on lines and commits, and several Git identities with avatars.

Remote over SSH

The repository stays on the server. You work on it from here.

Enter a host and a path. One engine runs behind both local and remote repositories, so everything on this page works the same on either.

  • Your SSH config, as ssh reads it. Host aliases, ProxyJump, Include, Match and identity files work with no extra setup.
  • Nothing to install on the server. SIT detects the platform, uploads its agent and tmux to ~/.sit and checks their sha256. No root, and the server needs no internet access.
  • Changes appear as they happen. Each repository is watched by the machine that holds it and changes are pushed to the window.
  • A slow server never blocks startup. Tabs restore independently; one that fails says why and can be retried.

Terminal

Terminals that are still there tomorrow.

Every worktree has its own terminals, running in tmux on the machine that holds the repository. SIT ships tmux 3.8 and deploys it for you.

  • Sessions survive. Quit SIT, lose the connection or move to another computer: the session is where you left it, output included.
  • Split panes and your shell. Split right or down, pick any installed shell and pin one as a repository's default. On Windows, WSL sessions restore too.
  • Paste a screenshot. The image is saved in the worktree's git-ignored .sit/paste and its path is typed for you, which is what a coding agent wants.
  • Know when it's done. Tabs show what is running, and a notification arrives when a long command finishes.

Try it: drag a Ready card onto an agent, or just click the card.

  • A board that is yours. Your own lists, labels and saved filters. Cards are Markdown files on this computer or on a server, so they follow you between devices.
  • Several notes, one task. Drop cards onto each other to merge them, then turn the result into a prompt.
  • Drag to dispatch. SIT creates the worktree and branch on the machine that holds the repository and starts the agent in tmux with the prompt.
  • Agents report back. Through MCP they post progress, ask questions and submit for review. A “Needs you” mark shows on the board, the sidebar and in notifications.
  • It keeps going without the window. The agent daemon runs after SIT quits, and autopilot can dispatch from your Ready list overnight.
  • Your agents, your accounts. SIT only starts the command you configured. It never sees or proxies a coding agent's credentials.

Under the hood

Built on git itself, and on its measurements.

SIT does not reimplement Git. It drives the git binary you already trust, through the interfaces git documents as stable, and it was designed around what those interfaces can do on large repositories.

56ms

git status on a worktree of 101,600 tracked files, the call SIT refreshes with.

8.5ms

to read 10,000 objects through one long-lived cat-file process, the way SIT reads them.

900×

slower when a process is started per object instead, which is why SIT never does.

Design baselines measured on git 2.53 with a 200,000-commit repository and an 811 MB worktree. Your numbers depend on your hardware.

Only git's stable formats

Status, refs, worktrees and objects are read with --porcelain=v2 -z and friends. No parsing of human-readable output, no reading inside .git.

No shell in the path

Every git call is an argument list, never a command string, so a file or branch name cannot become a command.

Stale views don't write

Each write carries the version of the view it was made from. If the repository moved on in the meantime, SIT refuses and refreshes instead of acting on old state.

One engine, two transports

The same agent serves the repository on this computer and the one behind SSH, so local and remote cannot drift apart.

Native, not a bundled browser

Written in Go with Wails, using the system WebView. The agent is a single static binary for Linux, macOS and Windows.

Traceable when it fails

Every operation carries a trace ID from the click to the git process, and errors show it. Logs redact secrets.

macOS won't open it the first time?
  1. macOS 15 or later: open SIT, click Done on the warning, then go to System Settings → Privacy & Security and choose Open Anyway.
  2. macOS 14 or earlier: Control-click SIT in Applications, choose Open, then Open again.
  3. If it says SIT “is damaged”, run this in Terminal and open it again:
xattr -dr com.apple.quarantine /Applications/SIT.app
